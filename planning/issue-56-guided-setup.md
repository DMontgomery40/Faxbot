# Issue 56: guided setup implementation slice

The first slice adds a seven-step, read-only dense-pages guide to the capability page and `faxbot savings capabilities setup dense_pages`. Both consume the existing capability read, including current saved page settings for enabled sending routes. No second settings writer or new permission is introduced. The canonical route switch still saves immediately; recipient edits keep their separate save boundary. The console keeps only the current review step in tab-local session storage and returns to capability status. Reviewing steps never records recipient agreement, verifies interoperability, activates settings or sends a document.

## Design and validation plan

Use a shared server-authored guide instead of duplicating setup policy in the console and CLI. An embedded replacement editor would duplicate validation and save behavior; a general change-staging system is outside the parent specification. Keep direct settings links on every step. Test the seven-step contract, canonical links, local route state, console recovery and cancellation, CLI parsing/output, authorization through the existing read, and console/CLI and settings coverage. Run affected tests and a console production build with at most two workers. Use only synthetic installations and local mocked providers.

## Precisely what remains

This slice does not close issue 56. The following work remains:

- Add guides for sending together, direct partner enrollment, T.38 and SSL Fax. Include resource-specific facts, actual agreement evidence and verification limits for each. Do not infer agreement from reviewed steps.
- Give the dense-pages guide a selected cloud route and recipient context, with route-specific prices, learned compatibility, write permission and provenance checks. The present guide reports enabled sending routes, including trunks, but does not assert that any selected route or recipient is eligible.
- Connect the canonical editors' lifecycle to the guide: independently saved sections, unsaved field drafts and pending activation must be recovered and distinguished. The present guide recovers only review position and says explicitly that it cannot recover unsaved edits in another editor. The long-pages switch itself has no pending activation stage.
- Provide consistent progress recovery outside the current browser tab and in the CLI if needed by the completed workflow. The CLI currently prints the entire guide and fresh saved state; it stores no progress.
- Add end-to-end synthetic tests of those editor handoffs, resource selection, permission changes, stale/failed reads, and all four remaining flows. The guide itself offers no live verification action; any future remote operation must retain its own explicit labelled control.
- Perform the rendered desktop/mobile keyboard usability review separately. No live fax, email, provider-account operation or customer validation belongs in this task's automated checks.

README status must continue to describe this as a partial A4 implementation. Operator guides are generated by Docs Autopilot after integration; builders maintain the CLI reference from source.

The initial combined run caught repeated schema reflection from the new guidance read. The implementation now passes the existing cached page-settings store to the canonical route view. The final combined run above includes all corrected cases.
