# Durable outbound delivery

Status: primary implementation design under independent review. Implements the approved whole-product refresh; no additional user approval is needed. This slice finishes outbound acceptance, dispatch, status/recovery and their operator flows. Inbound receipt acquisition and full RBAC have separate subsequent implementation slices, but this work must provide stable profile/principal seams for them.

## Required behavior

A successful acceptance survives API process death. Two API workers cannot submit the same accepted job concurrently. A crash or timeout after submission might have reached the provider must never cause blind re-submission. Callback, poll and submission responses cannot regress a terminal result. Every operation uses the job's immutable accepted revision and profile, including old credentials and manifest snapshot. A fax accepted while sending was disabled remains held permanently unless the operator submits a new explicit request; enabling sending never releases those test jobs.

Keep existing fax response fields and routes. Add delivery state, attempt and reconciliation information without renaming successful existing fields. Clients can optionally supply an Idempotency-Key scoped to their authenticated principal; the same key and original request content returns the existing job, a different request conflicts. Do not persist bearer credentials as the principal identifier or idempotency key. Existing historical jobs have no proof of whether a background submission already ran and must not become eligible automatically.

## Persistent delivery module

Add revision 0004 with additive tables independent of the historical ORM/migrations:

- `outbound_deliveries`: job ID primary/foreign key, accepted dispatch mode, state, current attempt ID, claim owner/token/expiry, request fingerprint, nullable principal scope/key digest, created/updated timestamps. One unique principal-scope/key-digest pair when a key exists. Artifact path comes from the captured revision's immutable data directory and stable job ID; do not resolve through later active settings.
- `outbound_attempts`: immutable attempt identity, job FK, sequence, profile FK, phase, provider SID, safe error category, submission timestamps and completion timestamps. A claim creates the attempt; the transition into submission is committed before crossing the external side-effect seam.
- `outbound_events`: bounded structured transition history with event identity/deduplication key and job/attempt association. Do not store raw fax contents, credentials, tokens, arbitrary remote error bodies or full callback bodies.

The delivery store is the only writer of job delivery status/provider SID/error after acceptance. It uses short SQL transactions with SQLite BEGIN IMMEDIATE and PostgreSQL row/advisory ownership compatible with the existing configuration lock order. Callback, polling, worker acknowledgement and operator reconciliation cross the same transition interface. No database transaction stays open across network, conversion or subprocess work.

New acceptance commits fax row, immutable binding, delivery row and initial event in one transaction under the existing active-revision check. Preparation failure cleans artifacts; uncertain database acknowledgement retains them and returns the identifiable job for reconciliation, as now. A same-key concurrent duplicate returns the prior durable job and cleans only its own unused preparation artifacts. Replays must not depend on the currently selected provider. Add original-upload SHA256 to PreparedDocument while streaming, before conversion (generated PDFs need not have byte-identical metadata); fingerprint destination, original bytes, document display name and queue-only intent with an explicit version. Principal comes from successful authentication, never a client-supplied owner field. Legacy bootstrap and development identities have explicit installation-local scopes; RBAC can replace this identity adapter later without exposing token material.

## State and crash rules

1. Acceptance creates `held` for disabled sending or `ready` for normal delivery. Historical rows are enrolled as terminal only when their stored terminal result is clear; every other preexisting row is `reconciliation_required`. Do not invent provider bindings for legacy rows.
2. An atomic ready claim creates a unique attempt and changes state to `preparing` with a bounded lease. Before external effects, validate captured artifacts and provider configuration, prepare callback/document grants, and confirm the claim is current.
3. Persist `submitting` immediately before calling the adapter. Only the holder of that attempt's token may cross this seam, once. A lost commit acknowledgement at this point must refuse submission until durable ownership is unambiguous; conservative reconciliation is acceptable.
4. A lease that expires in `preparing` can be reclaimed because no external submission has begun; its old token is fenced out. A lease that expires in `submitting` becomes `reconciliation_required`; it can never be reclaimed for another send. Stop/shutdown cancellation follows the same rule.
5. A confirmed provider acceptance stores its remote SID and changes to `in_progress` or the normalized terminal outcome. A timeout, dropped connection, cancellation or malformed response after crossing submission becomes `reconciliation_required`. Only a documented, definitive rejection may become `failed`; no generic exception is proof of non-delivery.
6. A late response from the same submitted attempt may reconcile an unknown outcome, but cannot overwrite an already terminal result or an operator-resolved/new attempt. Callback before submission acknowledgement is supported with guarded merge of remote identity. A mismatched remote SID/profile is refused and audited.
7. Held work is never claimed. Terminal states are absorbing for ordinary callbacks/polls/replies. Conflicting terminal events are recorded as conflicts without rewriting history. Status normalization is centralized; current lowercase/uppercase aliases map consistently, and unknown provider statuses never manufacture success/failure.

Use one asynchronous worker per API lifespan with database ownership supporting multiple processes. Start only after runtime is ready; stop and join before releasing installation resources. Blocking database work runs off the event loop. Poll frequency and bounded lease duration are implementation constants initially, not another configuration surface. The worker recovers eligible work on startup and periodically; it does not rely on a request's BackgroundTasks object. Shutdown joins or cancels transport work within its bound, records conservative uncertainty where possible, and leaves crash-safe durable state otherwise.

## Transport and callbacks

Separate the external submission adapter from database transitions. HTTP adapters return a normalized receipt or categorized error; AMI/FreeSWITCH use the same receipt/event contract while their resource ownership stays with lifespan. No adapter writes FaxJob directly. There is no assumed provider idempotency guarantee: enable a provider-specific retry policy only with a verified documented contract; otherwise at most one automatic submission attempt.

For status and callbacks, look up the bounded job/attempt candidate before verifying with its captured profile. Use provider-specific documented signature rules, captured callback URL/credentials and matching provider identity. Do not authenticate arbitrary events against current global credentials or try every historical account. Query job ID alone is not authentication. Where a provider callback does not include local identity, match its remote SID within the explicitly addressed account/profile and require an unambiguous result. Internal telephony events must refer to the owned connection/profile and active attempt. Preserve current callback paths with additive attempt identity parameters where supported.

Provide safe provider status reconciliation for supported adapters using stored remote SID. A missing SID after an ambiguous send requires explicit operator resolution; no polling by current configuration and no silent resend. UI exposes the reason, original provider identity, timestamps and transition history, with a deliberate reconciliation action. Operator action requires administrative authorization now and the dedicated RBAC permission once that slice lands; resolution is auditable and carries a loaded version condition. Explicit retry, if exposed, creates a new linked request only after a definitive non-delivery decision and unmistakable confirmation; do not auto-retry unknown delivery.

## Retention and verification

Retain artifacts for held, preparing, submitting, in-progress and reconciliation-required work. Finalized retention runs against captured locations and must not interpret generic failed legacy records as evidence for safe resend. Tokens remain scoped/expiring and logs remain redacted.

Internal verification covers real SQLite and PostgreSQL transactions, concurrent workers, all crash windows, cancellation, lost acknowledgement, duplicate acceptance, callback ordering and profile rotation. These are supplemental. All user-facing acceptance uses real Browser/Computer clicks/keystrokes: submit through Send, inspect Jobs/detail, observe restart recovery, held-mode persistence and reconciliation. A controlled local provider simulator may supply transport responses/callbacks, but the initiating acceptance and operator actions occur through the GUI and the evidence is labeled simulated. External real send/receive remains a distinct required release gate. Record every observed UI defect in the scratchpad for Sol repair and repeat the GUI path.

## Review rulings and implementation constraints

- Revision 0004 requires a whole-installation stop. Before any pending schema upgrade, startup must own the exclusive lifecycle lease; a shared/rolling starter refuses the upgrade rather than running new delivery tables alongside old background-task/callback writers. An already-current schema can still start multiple workers normally. Document the stop/backup/upgrade/start sequence and prove an old serving lease prevents migration.
- Existing generic `failed` is not proof of non-delivery: old helpers write it after arbitrary transport or post-submission database exceptions. Preserve the legacy reported value in migration/history evidence and classify these jobs for reconciliation; neither retention nor AMI drain may silently trust that value after the upgrade. Clear historical success stays recorded, but no historical row becomes dispatch-ready. Ambiguous cancellation/disabled labels require the same conservative treatment unless captured acceptance proves held mode.
- A database fence cannot revoke a request already issued or a process paused after receiving submission authority. An operator cannot release/retry an expired submitting attempt merely because its lease expired. Any explicit new send requires the prior issuer to be quiescent and definitive non-delivery evidence; this slice exposes reconciliation/status refresh, not a generic automatic Retry control.
- Require an authenticated attempt locator in provider callback URLs wherever supported. If a provider only returns its remote SID and a verified account-scoped callback can precede submission acknowledgement, persist a bounded, normalized unmatched event under that explicitly addressed account, then attach it only after the matching SID is durably recorded. Never guess among jobs or search/try arbitrary historical secrets. If no safe bounded identity is available, reject or quarantine for operator reconciliation rather than updating a guessed job. Event retention and size are bounded; do not retain raw callback payloads.
- Authenticate and resolve idempotency replay before rejecting it due solely to a newer active provider/mode. Replay still validates original request fingerprint and current principal permission, then returns the existing job. A new request continues to obey active configuration and queue-only guard. After rotation/restart, same key must never create a second job or require the new provider to prepare the old request's artifacts.

### Initial frozen schema contract

All tables use string `id` primary keys (40), naive UTC DateTime timestamps and explicit application values, matching the existing guarded schema validator. Use ordinary unique indexes rather than partial indexes or database-specific defaults.

- `outbound_attempts`: `id`, `job_id` FK fax_jobs (CASCADE), `sequence` Integer, nullable `profile_id` FK provider_profiles (RESTRICT), `phase` String32, nullable `provider_sid` String100, nullable `error_category` String64, `created_at`, nullable `submitted_at`, nullable `completed_at`. Unique index `(job_id, sequence)` and ordinary `(job_id)` index.
- `outbound_deliveries`: `id` FK fax_jobs (CASCADE), `dispatch_mode` String16 (`normal`, `held`, `legacy`), `state` String32, `version` Integer, nullable `attempt_id` FK outbound_attempts (SET NULL), nullable `claim_owner` String40, nullable `claim_token` String64, nullable `claim_expires_at`, nullable `next_poll_at`, nullable `request_fingerprint` String64, nullable `principal_scope` String100, nullable `idempotency_digest` String64, nullable `legacy_status` String32, `created_at`, `updated_at`. Unique index `(principal_scope, idempotency_digest)`; ordinary `(state, claim_expires_at)` and `(next_poll_at)` indexes. New keyed acceptances require both scope and digest in the store; nullable legacy/unkeyed rows are intentional.
- `outbound_events`: `id`, `job_id` FK fax_jobs (CASCADE), nullable `attempt_id` FK outbound_attempts (SET NULL), `kind` String40, nullable `dedupe_key` String64, `details` Text (bounded sanitized JSON), `created_at`. Unique index `(job_id, dedupe_key)` and ordinary `(job_id, created_at)` index. Nullable dedupe keys allow ordinary transition events; authenticated callbacks use stable scoped fingerprints.

Migration creates delivery records for existing fax_jobs with mode legacy, version1, original legacy_status, and state success only for the unambiguous stored aliases success/completed/completed_ok; all other historical states are reconciliation_required. It does not rewrite fax_jobs, infer profiles, create fictitious attempts or delete artifacts. Runtime can recognize proven captured disabled-mode jobs and classify held through an explicit audited store transition later. Migration history details preserve original statuses. The API/UI must show delivery.state as the actionable state while retaining the original reported value for reconciliation evidence.

### Replay and operator intent details

The web Send form creates one submission key per prepared user intent and retains it after a timeout/uncertain response; changing the destination/document or explicitly starting a new fax creates a new key. It must not silently generate a replacement key when retrying the same submission. The server stages/hashes bounded original bytes before conversion, resolves an existing scoped key using its stored request constraints, and only converts/selects a current provider for a genuinely new acceptance. Current authentication/revocation still applies to replay. Store no raw key; compare a versioned digest scoped to the authenticated installation-local principal.

Disabling sending pauses new dispatch authorization for normal ready jobs too; it does not cancel a submission already authorized/issued. Claim-to-submitting checks the current active disabled flag under the same configuration ownership order as Apply. Previously held jobs remain held after re-enabling. Polling and callback reconciliation may continue for already-issued work. UI copy must distinguish stopping future dispatch from recalling a fax already submitted.

All post-upgrade retention and AMI drain decisions read durable delivery state, including legacy reconciliation records, rather than trusting the old FaxJob failed string. Until historical records have been classified, cleanup fails closed for them.
