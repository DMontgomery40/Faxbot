# Faxbot access control

Implements the user-approved complete RBAC requirement in `2026-10-02-faxbot-refresh-design.md`. Technical decomposition under existing execution authorization; it does not reduce the full product goal. Baseline: `9d7c600e`. Primary owns policy, compatibility and integration decisions; Sol6.1 xhigh workers implement bounded, reviewed tasks. User-facing acceptance uses real Browser/Computer input, never a route test as a substitute.

## Product outcome

A dedicated installation has named users and integration principals. Administrators manage users, groups, roles, scoped assignments, credentials and sessions in the existing console. An operator sees and acts on only permitted faxes/mailboxes. Disablement, credential revocation and changed permissions affect subsequent operations across all workers. Host execution is a distinct privilege plus its existing installation gate. No tenant platform, authorization traits or interchangeable identity-plugin framework is introduced.

## One access module

`api/app/access/` owns authentication, persistent identity/session state, the permission catalogue, resource visibility and authorized policy mutations. HTTP, WebSocket, SDK, MCP and mobile adapters use its decisions. They do not infer authority from `keys:manage`, role names, arbitrary traits, frontend visibility or client-supplied owner IDs.

Its public concepts are immutable `PrincipalContext`, `ResourceRef` and `AccessDecision`, plus `AccessControl` backed by `AccessStore(engine)`. Authentication returns identity and credential/session identifiers, not a cached authority snapshot. Authorization rereads current principal, credential/session and assignments. Typed failures expose safe 401/403/404/409 reasons without credential material. Unauthenticated, forbidden and stale-version outcomes remain distinguishable.

PrincipalContext also captures principal security version and the authenticated credential epoch (key binding security version; session source versions; keyed current-bootstrap fingerprint). These are identity freshness checks, never a permission cache. Acceptance checks them again under its shared transaction, including a key rotated while an upload was converting. A stale context cannot silently act as the newly rotated credential.

## Resource and role model

Use roles composed of a closed permission catalogue. Assign a role to a principal or group **at a resource**. This single assignment is the resource grant; do not add a parallel, inconsistent grant system. A role permits its operations on the assigned resource and descendants. Unknown permissions, unknown resources, malformed ancestry or disabled subjects deny.

Resources form a shallow explicit tree: installation root; personal container for each principal; mailboxes under installation; outbound fax under its accepted creator's personal container; inbound fax under its routed mailbox. Persist inbound routing rule-to-mailbox-ID bindings so a mailbox rename does not break future routing. New unmatched inbound records enter the unassigned legacy container until explicitly assigned; arbitrary labels never create grants. A directly shared fax can receive an explicit assignment. Unowned historical faxes are under a legacy container, not guessed from free-text owner/phone/file names. No direct nonadministrator assignment is created there by default. The same ancestry rules apply: installation-wide assignments deliberately cover all descendants, including legacy history; UI must identify this breadth. A migrated installation-wide metadata grant retains historical visibility, not document bytes or inferred ownership.

`ResourceRef` addresses stable resource IDs, never a mailbox label or arbitrary query filter. A mailbox rename preserves its resource. Current inbound routing labels are reconciled with stable mailbox IDs during ingestion. Lists, counts, search, metadata, downloads, refresh and reconciliation use the same resource ancestry and role decisions. An invisible individual resource returns 404; a visible resource with a denied action returns 403.

Built-in role definitions are immutable: Owner (all catalogue permissions); Administrator (ordinary identity/configuration/document operations, excluding host shell/actions and owner recovery); Fax Operator (send, owned/assigned outbound metadata/document/status and assigned inbound metadata/document); Fax Viewer (assigned metadata/document only); Auditor (security audit and permitted metadata, no documents); Host Operator (explicit host operations, diagnostics and required configuration read). Assignments establish scope; a Fax Operator at its personal container does not read all installation faxes. New users receive no fax or management assignment automatically. Owner creation is an explicit bootstrap operation.

Permissions are exact strings. Retain `fax:send`, `fax:read`, `inbound:list`, `inbound:read`, `keys:manage` where their existing ordinary meanings fit. Add `fax:document`, `fax:refresh`, `fax:reconcile`, `inbound:document`, `mailboxes:read`, `mailboxes:manage`, `users:read`, `users:manage`, `groups:read`, `groups:manage`, `roles:read`, `roles:manage`, `grants:read`, `grants:manage`, `sessions:read`, `sessions:revoke`, `settings:read`, `settings:write`, `providers:read`, `providers:write`, `providers:install`, `diagnostics:read`, `logs:read`, `audit:read`, `tunnels:read`, `tunnels:manage`, `tunnels:pair`, `host:restart`, `host:actions`, `host:terminal`, `owner:recover`. Global operations require an assignment at installation; fax send uses the creator's personal container. Metadata permission never implicitly grants document bytes or key management.

## Persisted schema and migration

Add locked revision `0005_access_control` after outbound0004, without rewriting frozen previous revisions. Add `access_state` (singleton policy version), `access_principals`, `access_users`, `access_groups`, `access_memberships`, `access_permissions`, `access_roles`, `access_role_permissions`, `access_resources`, `access_mailbox_routes`, `access_assignments`, `access_key_bindings`, `access_key_grants`, `access_sessions`, `access_audit`. Use explicit primary/foreign keys, uniqueness, bounded names and UTC timestamps; principal/group assignment exclusivity and resource-shape checks are validated both on writes and schema constraints. No nested groups. Roles, groups and subjects have revision counters for stale-editor rejection.

Principals have immutable ID, user/integration/bootstrap kind, display name, enabled state, security version and timestamps. Users have unique normalized login, password hash, password-change-required and password version. Sessions store only token/CSRF hashes, principal ID, created/last-used/absolute expiry, revoked timestamp and principal security version. Keys retain the current `APIKey` token/hash/ID format; a separate binding links each key to a principal and carries credential state/version. Key grant rows capture permission/resource ceilings. Audit rows persist actor, credential/session, operation, target, policy versions, outcome and bounded nonsecret details in the policy mutation transaction.

Migration creates a distinct integration principal for each existing DB key, preserving its token/hash/expiry/revocation. Never infer a human from `owner`. Preserve the five recognized ordinary scopes (`fax:send`, `fax:read`, `inbound:list`, `inbound:read`, `keys:manage`) as explicit permissions in a per-key immutable legacy role plus matching credential ceilings; unknown scopes are denied and reported. Assign the role at installation, preserving historically global metadata visibility. `keys:manage` maps only to constrained key management, never administrator/host access. Historical `inbound:read` no longer implicitly authorizes PDF bytes: record this deliberate narrowing and require explicit `inbound:document` regrant. Existing wildcard keys require explicit administrator migration review and receive no assignments or ceilings automatically. Bound outbound rows with a verified `principal_scope=key:<id>` can acquire that principal's personal resource; other historical rows stay in the legacy container. Record counts and migration decisions without tokens. Do not modify delivery states or persisted request replay identities.

The configured installation bootstrap key authenticates a dedicated bootstrap principal for initial Owner creation/recovery and explicit installation administration. It is not a staff identity or an inferred user. Retain its existing `key:env` replay namespace for compatibility and identify its privileged use in audit. Document replacing shared bootstrap use with named/scoped credentials. Once named Owners exist, destructive owner changes cannot remove the last enabled Owner with a usable login; serialize the check and mutation. The bootstrap recovery path remains available to the host operator with the configured installation secret.

Provide a stopped-installation, local host recovery command for an initialized database with no usable Owner and no configured bootstrap key. Configuration is imported from environment only on initial setup, so editing `.env` or calling reload is not recovery. The command uses the canonical locked store and audit, reveals a fresh recovery secret once through the host terminal, and does not expose a public bootstrap-without-secret endpoint.

## Authentication and sessions

Retain `X-API-Key` for integrations/mobile/SDKs. Browser users authenticate with username/password to an opaque persisted session, carried in an HttpOnly cookie. Provide an explicit key-to-session compatibility login. Do not put session or API-key secrets in URLs, logs, audit details or new persistent browser storage. Passwords use the existing salted scrypt primitive with fixed bounded parameters; no plaintext/default password. Administrative reset issues a one-time random temporary secret and requires change before ordinary operations. User password changes require the current password, rotate the current session and revoke other sessions. Disabled users cannot login, refresh, change password or use delegated keys.

Session lifetime: 12-hour absolute and 30-minute idle limits. A key-to-session login retains its source credential binding and version: every subsequent operation intersects current principal assignments with that key's ceiling and checks its revocation, expiry and rotation. Its expiry cannot exceed the key's expiry. A bootstrap session similarly binds to the current configured bootstrap secret version; deleting or rotating that secret invalidates the session. Password sessions are explicitly distinct. Sessions must never launder a restricted credential into principal-wide authority. Credential or account disable/revoke takes effect after the mutation commits for subsequent protected operations. Role changes are read live; no frozen permission set in sessions. Browser mutations require an exact allowed Origin and session CSRF header; API-key clients retain header authentication without cookie-based CSRF assumptions. Secure cookies on HTTPS, SameSite=Strict, host-only path `/`; explicitly local loopback development may use HTTP. Deployed remote access requires HTTPS through the operator's existing tunnel/reverse proxy.

Production authentication is mandatory even when old `REQUIRE_API_KEY=false` bootstrap data exists. Anonymous behavior requires a separate explicit deployment-only `FAXBOT_ALLOW_ANONYMOUS_DEV=true` gate and is visibly identified as development. Do not enable it from an ordinary Settings editor, infer it from a missing key or silently expose production. Health liveness/login/bootstrap instructions remain accessible without revealing private state. Readiness reports absent production authentication; ordinary operations refuse missing credentials.

## Delegation and revocation

A management permission permits editing a category; it is not permission to grant arbitrary authority. Issuing a key, assigning a role, adding group membership or expanding an assigned role must not produce authority outside the actor's current grantable permission/resource set. Role edits examine every affected assignment; membership edits examine the group's assignments. Assigning Owner requires the actor's explicit complete Owner authority. Validate changes and the last-Owner invariant under one access-state lock with optimistic policy/editor version checks. No silent reload-and-retry of stale editors.

Changing a target's login, password/reset state, credentials, enablement or identity must also pass authority dominance against the target's current direct and group-derived authority. Ordinary `users:manage` cannot reset or take over an Owner. Owner targets require explicit complete Owner authority; a current-password-authenticated self-change is a narrow exception. Preserve the canonical bootstrap `api_key` setting for compatibility, but replacement/clear and full-secret recovery export/persistence require `owner:recover` and complete Owner authority. Apply these checks to accepted canonical changes through every alias/import/plugin path. Ordinary redacted settings export remains `settings:read`.

A key's authority is the intersection of the enabled principal's current assignments and its captured permission/resource ceiling. Rotation preserves that ceiling and never revives a revoked/expired key or disabled principal. A user-delegated key is bound to that user; independent integration identities are explicitly managed separately. User disablement revokes all its sessions and delegated credentials atomically. Groups and roles are not credentials and cannot bypass principal disablement.

Lock order when acceptance needs both modules: configuration installation lock, then access-state lock. Access mutations never acquire the configuration lock. Outbound acceptance authorizes and assigns ownership inside its existing durable transaction. Already accepted work continues its captured delivery lifecycle after user disablement; revocation restricts new sends and access/actions, and does not implicitly resend/cancel issued faxes. Idempotency retains `key:<existing-id>` for key clients and their compatibility browser sessions, and `key:env` for bootstrap clients/sessions. Only password sessions use `principal:<id>`, stable across session rotation. An early replay lookup must revalidate the current credential, action permission and returned resource visibility before returning accepted-job metadata. Store/audit actor formats expand deliberately to stable principal/session identities.

The access module accepts the existing SQLAlchemy Connection for acceptance/replay authorization, access-state locking and resource/audit creation. It must not open a nested engine transaction while the configuration/delivery transaction is held. Standalone access mutations own their own dedicated transaction using the same access-state lock.

An explicitly supplied `X-API-Key` header is the sole attempted credential for that request. Invalid or empty explicit headers reject; they never fall back to an ambient session cookie. Without that header, authenticate the cookie and apply Origin/CSRF based on the actual cookie source, including compatibility sessions. This prevents stale client credentials and ambient cookies from silently selecting a different identity.

Restore CSRF after page reload without invalidating other tabs: derive the session's CSRF value reproducibly from the opaque session token with an installation-keyed domain-separated digest, store only its verification hash, and return the value from authenticated `/auth/me`. Do not rotate it on every identity read. Validate exact allowed Origins from explicit deployment/canonical URL configuration; never trust arbitrary Host or Forwarded headers as an allowlist. Authentication/login routes also reject cross-origin browser submissions. Bootstrap fingerprints use a distinct domain-separated installation-keyed digest; no raw bootstrap secret is persisted in access state.

## Integration and UI

Add `/auth/login`, `/auth/key-login`, `/auth/me`, `/auth/logout`, `/auth/password`, and owned-session management. Identity/group/role/assignment/key management routes use versioned typed requests and safe policy errors. Ordinary console startup reads effective identity/permissions instead of requiring `/admin/config`; each panel fetches only permitted data. Users, Groups, Roles, Resource Access and Sessions become working views in the existing Settings area. Show effective access, assignment scope, pending drafts, conflicts and explicit denied/empty states.

Replace every protected HTTP dependency, direct file route, administrative action and WebSocket handshake with operation/resource policy. Provider callback verification and provider-fetch capabilities stay separate from human sessions, preserving issued delivery access when an operator logs out. Terminal requires `host:terminal`, the installation execution gate, exact Origin and a short-lived one-use session-bound handshake capability. Recheck authorization before input and close revoked idle channels within five seconds. Host actions/restart/provider installation have their own permissions. Do not leave query-key compatibility as an unbounded browser bypass.

MCP HTTP/SSE transport sessions bind to authenticated subjects; distinct humans cannot silently inherit one configured administrator key. Stdio may explicitly represent its configured integration principal. iOS pairing creates a short-lived single-use pairing exchange and a bounded revocable device key; existing send/status/header contracts remain. Validate client error handling and effective resource access through real available clients; restoring historical source is not acceptance.

## Completion evidence

Internal SQLite/PostgreSQL checks cover migration, FK/uniqueness, atomic audit, group/role delegation, stale versions, resource filtering, revocation across stores/workers, session expiry and last-Owner races. Pure policy/protocol tests supplement actual GUI acceptance. Primary Browser/Computer creates and logs in controlled synthetic users, grants a mailbox/document, demonstrates restricted lists/downloads and denied guessed IDs through normal UI where available, revokes an already open session/key, verifies stale editors and logout, and exercises authorized terminal/client flows. Direct-call security tests run in authorized hosted CI; they do not replace user-facing checks.

RBAC is complete only when every named management flow, server enforcement path, resource restriction, client propagation, recovery/backup behavior and audit evidence is implemented and verified. Schema or Users CRUD alone is not completion. The broader refresh still requires inbound, native/provider delivery, docs publication and transferability proof.
